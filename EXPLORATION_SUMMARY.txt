1. EXISTING IMPLEMENTATION OVERVIEW
================================================================================

ARCHITECTURE STACK:
  Backend    : Express.js + Node.js (70 lines server.js)
  Frontend   : Vanilla HTML/CSS/JS (no frameworks)
  AI Engine  : Anthropic Claude Agent SDK with MCP integration
  Payments   : Locus MCP server (USDC transfers on blockchain)
  Streaming  : Server-Sent Events (SSE) - not WebSocket

CURRENT FLOW (2-party negotiation):
  1. Browser calls /api/chat/stream
  2. Server starts async generator conversationFlow()
  3. Query Seller Agent → yield to frontend
  4. Query Buyer Agent → yield to frontend
  5. Check agreement (both accept same price)
  6. If agreed: Execute payment via Locus MCP
  7. Stream done event

TOTAL EXECUTION TIME: 40-60 seconds (serial 20 API calls)

3. REAL-TIME COMMUNICATION ARCHITECTURE
================================================================================

TECHNOLOGY: Server-Sent Events (SSE) - NOT WebSocket

ADVANTAGES CHOSEN:
  ✓ Server → Client unidirectional (perfect for this use case)
  ✓ Native browser EventSource API (no library needed)
  ✓ HTTP-based (simpler than WebSocket upgrade)
  ✓ Text protocol over HTTP (works through proxies)
  ✓ Automatic client reconnection
  ✓ Heartbeat prevents proxy/firewall timeout

WHY NOT WEBSOCKET:
  ✗ Requires bidirectional communication (we only need → direction)
  ✗ Complex protocol handshake
  ✗ Needs WebSocket library
  ✗ More connection state management

COULD UPGRADE TO WEBSOCKET FOR:
  - User intervention (stop/pause/modify negotiation)
  - Real-time user input (chat-style)
  - Bidirectional chat (human + agent)

MESSAGE FORMAT (JSON over SSE):
  {
    timestamp: "2024-11-15T10:30:00.000Z",
    status: "default|success|error|processing|waiting|negotiating",
    audience: "buyer|seller|both",
    agent: "buyer|seller|system",
    text: "...",
    displayName: "Buyer Agent",
    summary: true/false,
    details: {...}
  }

SSE EVENTS:
  event: message
  data: {JSON payload}
  
  event: done
  data: {}
  
  event: error
  data: {JSON error}

4. AGENT ARCHITECTURE & COMMUNICATION
================================================================================

THREE AGENT ROLES:

1. SELLER AGENT
   - Price range: $0.01-$0.10 USDC
   - Starting price: Random $0.06-$0.10
   - Behavior: Start high, negotiate down
   - Goal: Accept highest price in range
   - System prompt includes price guidance
   - Queries after each buyer response

2. BUYER AGENT
   - Hard limit: $0.05 USDC (will reject above)
   - Behavior: Polite negotiation
   - Goal: Accept lowest price ≤ $0.05
   - System prompt includes budget constraint
   - Queries after each seller response

3. SYSTEM AGENT
   - No AI queries (deterministic logic)
   - Manages negotiation flow control
   - Executes payments
   - Sends audience-specific messages (buyer-only, seller-only, or both)

AGENT COMMUNICATION PROTOCOL:

1. System: "Starting negotiation..."
   ↓
2. Query Seller Agent (empty transcript + system prompt)
   → Seller: "I'm selling this PDF for $0.08"
   ↓
3. Add to NegotiationState.transcript
   ↓
4. Query Buyer Agent (full transcript + system prompt)
   → Buyer: "That's high. Can you do $0.04?"
   ↓
5. Check agreement (both said accept words AND price within limits)
   ↓
6. Loop (max 10 turns) or execute payment if agreed
   ↓
7. If agreed: sendPayment() via Locus MCP → Claude calls tool

CONTEXT PASSING:

Each agent receives full conversation history:
  "Seller Agent: I'm offering this PDF for $0.08 USDC
   Buyer Agent: That's a bit high. Can you do $0.03?
   Seller Agent: I can come down to $0.06
   Buyer Agent: I accept $0.06"

This allows agents to:
  - Understand negotiation progress
  - Learn counter-party's position
  - Make informed responses
  - Detect agreement conditions

TOOL ACCESS:

- Seller & Buyer agents: Access Claude SDK with MCP tools
- System agent: Direct Locus MCP tool calls for payment
- Authorization: canUseTool() callback enforces budget limits
- Only Locus tools allowed (payment safety)

5. PAYMENT & AUTHORIZATION FLOW
================================================================================

PAYMENT PIPELINE:

1. Agreement reached (buyer and seller accept same price)
   ↓
2. System: "Agreement reached! Price: $0.05 USDC"
   ↓
3. executePayment(agreedPrice) async generator
   ├─ System: "Sending $0.05 to seller..." (audience: buyer)
   ├─ System: "Buyer sending $0.05..." (audience: seller)
   │
4. sendPayment({to: RECEIVER_ADDRESS, amount, memo})
   ├─ Prompt: "Send 0.05 USDC to 0x4ae... with memo 'PDF purchase'"
   ├─ Claude SDK queries Claude API with MCP options
   ├─ Claude calls mcp__locus__send_to_address tool
   ├─ Locus MCP executes blockchain transaction
   └─ Returns transaction ID
   │
5. extractConfirmationId(payment.result)
   ├─ Looks for: transaction_id, transactionId, id, tx_hash, 0x hash
   └─ Returns transaction ID string
   │
6. System: "Payment confirmed. TX: 0x123abc..." (audience: buyer)
   System: "Payment received. TX: 0x123abc..." (audience: seller)
   │
7. Seller: "Here's your PDF: <a href='...'>Download</a>"
   Buyer: "Thanks! Access here: <a href='...'>Download</a>"

TOOL AUTHORIZATION:

Authorization callback (canUseTool):
  
  1. Check tool name starts with 'mcp__locus__send_to_address'
     └─ Enforce buyer spending limit ($0.05 max)
     └─ Deny if amount > BUYER_LIMIT
  
  2. Check any 'mcp__locus__*' tool
     └─ Allow with behavior: 'allow'
  
  3. All other tools
     └─ Deny with behavior: 'deny'

SPENDING LIMITS:

- Hard limit: $0.05 USDC (buyer cannot exceed)
- Enforced at: canUseTool() authorization layer
- Tool: mcp__locus__send_to_address
- Status: "Amount 0.08 exceeds buyer limit of 0.05"

ALTERNATE PAYMENT METHODS:

- Explicitly prevented in seller system prompt:
  "Never suggest alternate payment methods (no email, escrow, or other wallets)"
- Only RECEIVER_ADDRESS accepted
- Only USDC currency accepted

8. CRITICAL PATTERNS & DESIGN DECISIONS
================================================================================

PATTERN 1: Async Generators for Streaming
  Why: Perfect for yielding items over time to SSE
  Benefit: No need to collect all messages before sending
  Extension: Can yield from Promise.race() for parallel responses

PATTERN 2: Audience-Aware Messages
  Why: Different information for buyer vs sellers
  Benefit: Seller doesn't see buyer's budget; buyer sees comparisons
  Extension: Per-supplier custom messages

PATTERN 3: In-Memory State Classes
  Why: Simple, fast, no database needed for demo
  Benefit: Easy to extend with new fields
  Limitation: Lost if server restarts (OK for demo)

PATTERN 4: Regex-Based NLP
  Why: Lightweight, deterministic, fast
  Benefit: Works without ML, easy to debug
  Limitation: Fragile with creative language

PATTERN 5: Tool Authorization Callbacks
  Why: Claude can call tools, but we control what's allowed
  Benefit: Enforce budget limits, prevent escape attacks
  Limitation: Requires careful prompt engineering
